# 任务状态路线图

## 当前状态

当前发布版本没有可验证的受支持通道，用于订阅官方 Codex/ChatGPT 桌面应用已经运行的任务。因此任务色点只是一项默认关闭的 UI 预留，不承载真实状态。

## 路径 A：官方桌面会话观察（首选）

若 Codex 将来提供公开、稳定的 observer API，接入条件如下：

1. 可只读连接官方桌面应用正在使用的会话；
2. 可获得 thread/turn ID、开始、成功、失败、中断、审批和阻塞输入事件；
3. 可断线恢复并列举活跃任务；
4. 不需要提取令牌、修改应用包或使用辅助功能抓屏。

完成后才可启用语义颜色：红（需要处理）> 黄（运行）> 绿（最近成功完成）> 灰（未知）。

## 路径 B：Meter 托管任务（独立产品方向）

Meter 自己创建 `thread/start`、`turn/start` 并持有同一 app-server 连接。这样可以准确显示它发起的任务，但不能覆盖用户直接在官方桌面界面创建的任务。

最小技术 Spike：

- 创建一个临时、无副作用任务；
- 验证 started、completed、failed、approval、blocking input、cancel 和重连事件；
- 验证同一 thread/turn 去重；
- 验证是否能在官方桌面安全定位该 thread；
- 验证该任务是否会稳定出现在官方桌面历史中。

只有 Spike 成功后，才决定是否建设任务创建窗口、审批 UI、输入 UI、任务详情和持久化。

## 不采用的路径

- OCR 或 Accessibility 抓取 Codex UI；
- 解析私有通知数据库；
- 读取认证令牌、Keychain、进程内存；
- 基于“长时间没有日志”推断任务已完成；
- 将非公开 HTTP 接口作为生产依赖。

这些路径要么不可靠，要么破坏安全边界，都会导致错误的菜单栏颜色。
